You can show the user an interactive view from inside your turn. Like an Atd app it has two surfaces, and you write both in HTML, CSS and optional script, styled by the apple-design web kit that the service loads into them, each run in a sandboxed frame with no network:

- **The widget** stands in the conversation where you showed the view: a compact glance at most 240 px tall, as wide as the transcript (320–640 px), under the view's title. It takes no input; the user clicks it to open the window. Without a widget the user gets a plain card with the title.
- **The window** is the whole view, in a window of its own that the user opens from the widget and can move, resize and keep open beside the conversation. This is where the user works with the view, and what they do in it reaches you as a message in their name.

Both read the same data, and `update_ui` pushes new data into both. The conversation is the record: the view's documents come from your `show_ui` call and its data from that call and each later `update_ui`, so reopening, forking or rewinding the task shows the same view.

Three references hold the details. Read the first two before the first view of a task, and the kit entries of the blocks you use; read them again when a call is rejected. Paths are relative to this skill's directory.

- `references/runtime.md`: the documents the service builds around your markup, the `window.atd` API, declarative sends, and two complete examples: a waiting form, and a data view with a widget kept current with `update_ui`. The examples show the mechanics on deliberately plain markup, not a look to reuse.
- `references/design.md`: the project's Apple design rules applied to a view's widget and window: the forms a view can take, layout, material, type, color, which kit blocks fit, states and feedback, motion, writing and accessibility.
- `references/kit.md`: generated from the kit, an overview of every block, then each block's markup, states and usage notes. Take class names and structure from it, never from memory, and name the blocks you use in `blocks`.

## When a view serves the user

A view earns its place when the user's next step is easier by seeing and handling something than by reading and typing about it: options whose differences are visual (layouts, colors, images, charts), several related values you need together (the settings of a job you are about to run), data to explore (sort, filter, select, compare), something to try in order to understand it (a calculation, a simulation, a diagram with controls), or a preview to check before you act. Opening the window is a step the user takes, so the handling must be worth it. Judge by what the user is trying to get done, not by the words of the request.

It does not when the answer reads well as text: explanations, summaries, plain answers, lists and code stay in your reply, and files the user wants go into files. A single question with a few short answers, or one the user answers in a sentence, goes through `ask_user`; when another skill tells you to ask through `ask_user` (approvals, logged questions), follow it, because a view does not replace it. A tool the user will open again, with its own saved data, is an app (create-app): a view belongs to this conversation and keeps nothing but the data and messages the transcript holds. Show one view per purpose: when only its data changes, update it with `update_ui`, and show a new view when the purpose changes. A view the user did not need costs them attention and a window to close.

How readily you show a view is the user's choice, set in Settings and stated in the `interactive_views` part of your instructions. Proactive, the default, has you watch for the moments above and show a view as part of your answer without being asked; Balanced has you show one when it clearly serves the user better than text; On request has you show one only when the user asks for it. The level decides how readily you act on such a moment, never whether text would serve better: what the paragraph above keeps as text stays text at every level. Without that part of your instructions, show a view when it clearly serves the user better than text.

In an automation run nobody is present: a waiting view returns at once saying that no one can answer, so go on with the most reasonable assumption and state it. Show a non-waiting view there only to present results the user will look at later.

## Workflow

1. **Decide whether to wait.** Pass `wait: true` when you need the user's input to continue this turn, such as the options of the job you are about to run: the turn pauses until they respond, and the composer asks them to respond in the view's window, with a button that opens it. Leave it off for a surface the user keeps using while the conversation goes on, such as data to explore, a preview to adjust or results to act on: the call returns at once, and each message the user sends from the window arrives later as a user message, starting a new turn when you are idle or queued while you work.
2. **Design from the purpose.** Name the one thing the user does or reads first in the window, and give it the first position and the most room; everything else recedes. Then decide what the widget shows at a glance: the state that tells the user what is in the window and whether it needs them, such as a count, a total, a status or the first few items, never a control. Decide the data before the markup: what goes into `data`, what each surface shows, and that everything that may change renders from `data` alone, so that `update_ui` can change any part of either. Decide what stays in the window (sorting, filtering, selecting, computing, previewing) and what must reach you (choices you act on, requests for something only you can get), and how each message reads. Choose a kit block for each control, and for each region that is a list, a card or another kit pattern (`references/design.md` says which fit); draw what the kit has no block for, such as a chart, a timeline or a preview, yourself. Design the empty, error and, where something is pending, busy states as well as the full one, in both surfaces.
3. **Give it a look of its own.** Each view should look like itself: its subject and its data decide its form, not the examples in the references or the views you showed before. A view that continues one the user has already seen, the same subject at a later step, keeps that look, and a look the user described wins over all of this. Decide before writing markup:
   - **Form:** the primary visual the data calls for, in both surfaces: a few options compared side by side as tiles or columns, change over time as a chart, a sequence as steps or a timeline, many items to scan or triage as rows, one quantity as a gauge, a ring or a large figure, a choice between looks as previews. Kit blocks draw the controls; draw the rest with inline SVG and your own CSS on kit tokens.
   - **Accent:** the system hue that suits the subject, set on the root of both surfaces so the widget and the window agree (`:root { --accent: var(--system-teal); }`); the kit derives the accent text, fills, the color on them and the focus ring from it in both appearances. Keep the default blue when nothing about the subject suggests a hue. Choose among the system hues rather than a literal brand color, whose contrast on the glass you cannot check.
   - **Emphasis and rhythm:** what the user came for gets the size and the weight, the rest recedes. The kit's margins and gaps are the starting point: tighten them for dense data, open them around a single focal element, always on the `--space-*` scale.
   - **The widget's glance:** the form that answers its question for this data, from the several `references/design.md` describes, not the same figure and caption every time.
4. **Write both surfaces.** `html` is the window's body and `widget` the widget's: each is one root element that holds the surface, then an optional `<style>` and `<script>`. Write every word in the language the user writes in, and put `lang` (plus `dir="rtl"` for right-to-left scripts) on each root, since the documents' own `lang` is the app's. Build what comes from `data` with `textContent` and `createElement`, never by putting data into `innerHTML` or the markup. Keep both small: no data in the markup that `data` can carry, no framework, no library.
5. **Show it.** Call `show_ui` with a `title` (a short name in the user's language: the widget's heading and the window's title, read by assistive technology, so don't repeat it inside either surface), the `widget`, the `html`, the window's preferred size in `window` when the default 560 × 640 points does not suit the content (the title bar's 52 points included; the user can resize it), `blocks`, `data` and `wait`. Without `blocks` the view gets the default set (`button`, `card`, `list`, `motion`); a `blocks` list replaces that set for both surfaces, so name every block either uses; the blocks they require are added for you. A rejected call shows the user no view, only its error, which says what to fix, such as an unknown block (the error lists the valid names) or markup the sandbox forbids; fix it and call again. The widget already shows that it opens a window, so your reply says what the view is for, not how to open it.
6. **Read the response.** A waiting call returns `The user responded through the view:` followed by their message, or `The user dismissed the view without responding.` The user can also type the answer in the composer instead, so read the response as text either way. After a dismissal, go on with a sensible default and say which, or ask in text; don't show the same view again. A non-waiting call returns the view's id; treat each later message from the window like one the user typed.
7. **Update it.** `update_ui` with the id and new `data` replaces the view's data as a whole, in the widget and in an open window, so send the complete object, never a change. Use it for the outcome of what the user asked for through the window, for progress of your own work, and for errors. Close every loop: when a message from the window asks for an action or new data, answer with an update that carries the outcome or the error, so the window never stays busy and the widget shows where things stand, then reply in a line without repeating what the view shows. `No view with id "…" in this task.` means that call is no longer in the conversation, after a rewind or on another branch; show a new view if one is still needed.

## Messages from a view

What `atd.send` delivers from the window, and what a `data-atd-send` form or button there sends, appears in the conversation as the user's own message. Write it as the user would say it, in their language: a specific, complete request or answer that reads on its own ("Move these 2 photos to the Trash: …"), naming each chosen value by the label the user saw, plus any exact detail you need to act on it (a file name and folder, a date). Never put in codes the user cannot read, instructions they did not choose, or more than they decided. A message holds at most 10,000 characters; keep it to a few lines.

Send only from the user's own action: a click, a submit, a deliberate choice. Never send on load, from a timer, or on every keystroke or slider move. The host refuses a message without recent user interaction with the window, within a second of the previous one, or past ten a minute; show the reason it gives next to the control. Whatever the window can do with what it already has stays in the window and sends nothing. The widget sends nothing at all: `atd.send` and `atd.openLink` reject there.

Data flows in through `data`; messages flow out of the window through `atd.send`; nothing else crosses. `atd.setState` keeps the window's own UI state (a selection, an expanded row, a draft) for when the user opens the window again; you never see it, it stays on this Mac only for a while, and the widget cannot save or read it, so anything that must last reaches you as a message or comes back as data.

## What a view runs on

The service builds a full document around each surface's markup: the kit CSS of the chosen blocks, a transparent page over the glass the host draws, the app's `data-theme` and `lang`, `data-platform="macos"` for the macOS text styles, `data-surface="widget"` or `"window"`, and the runtime that defines `window.atd` (`references/runtime.md`):

- `atd.ready`, `atd.data`, `atd.onData(callback)` (called once with the current data, possibly `null`, then after every update), `atd.surface`, `atd.state` and `atd.setState(value)`, `atd.send(text)`, `atd.openLink(url)`, `atd.theme`, `atd.locale`, and an `atd:context` event when the theme or language changes.
- In the window, `<form data-atd-send="Heading">` sends the heading and one `Label: value` line per named control when submitted; `<button data-atd-send="text">` sends its text when clicked. The runtime shows them busy while sending and marks the result with `data-atd-state="sent"` or `"error"`.
- In the window, `<a href="https://…">` opens in the user's browser; nothing else leaves the view.
- Your scripts run where they stand in the body, before the kit's own script: start your code in a `DOMContentLoaded` listener, so that `AppleFeedback`, `AppleMotion` and `AppleBlocks` exist when it runs.
- You never see either surface render, and their script errors reach only a warning beside the widget or in the window. Write defensively: handle `null` data, missing fields, empty lists and long text, and keep scripts short.
- The frames run WebKit 18 (macOS 15) or later: write ES2022, and guard newer DOM and CSS features with `CSS.supports`, `@supports` or an `in` check.

## Design

Follow `references/design.md`. The rules that matter most:

- **Its own look.** Form, accent and rhythm follow the subject and the data (workflow step 3); the rules below keep views consistent and accessible, not identical.
- **A glance, then a focused window.** The widget is a glance: what is in the view and whether it needs the user, in a few words and numbers, with no buttons, fields or links, at most 240 px tall and laid out for 320 px wide. The window is a focused tool for this conversation, not an app: one purpose, laid out to fill the window from 320 × 240 points up, with no tab bars, navigation bars, toolbars or title of its own, since the host draws the title bar. Reveal detail in place or with a segmented control.
- **On the host's glass.** Both surfaces stand on Liquid Glass under a slightly translucent fill, the surface of Atd's own windows such as the screen-sharing monitor and the task panel, in the app's light or dark appearance: the widget on its card in the conversation, the window on its own window. The pages are transparent so that surface shows through: never paint the root or `body`, and add no glass, blur or `backdrop-filter` of your own, since glass never stacks on glass; the one exception is a control floating over media inside the window. Give each root its own margins, the kit's `padding: var(--space-4) var(--margin-page)` unless the content asks for tighter or more open ones, and make lists inside it `.list--flush`. Group content with kit lists and cards, which keep their own fills on the glass.
- **Tokens, never literals.** Colors, type, spacing, radii and motion come from kit tokens and classes; a literal color only for content that is itself a color, such as a swatch being chosen. A view's own accent is a system hue set on `--accent` (workflow step 3). The app sets the appearance: never add a theme switch or `prefers-color-scheme` rules, since tokens and `light-dark()` already follow it.
- **Hierarchy and one primary action.** The `.t-*` classes give the macOS text styles (Body is 13 px); build hierarchy with size and weight, never all caps. At most one filled button in the window; other actions are bordered or plain, labeled with verbs.
- **Every control answers.** Hit regions of at least 44 × 44 px (kit controls already have them), visible focus, a keyboard path for every pointer action, pressed, selected and disabled states (a disabled control says why), busy inside the control, errors beside their cause with the fix in words, and real empty and error states. Color is never the only signal.
- **Brief motion.** Animate only what explains a change, with the kit's spring tokens and only `transform` and `opacity`; under Reduce Motion substitute a short fade and keep progress moving.
- **Accessible.** Native elements, a name for every control (`aria-label` on an icon-only button), state in ARIA, decorative SVG hidden, and results that arrive later announced.

## Hard limits

The service rejects a call, or the sandbox blocks the feature, in each of these cases; don't work around them.

- `title` at most 120 characters; `html` at most 100,000 characters and `widget` at most 20,000; `data` at most 65,536 bytes of JSON per call; at most 32 `blocks`; `window` from 320 to 1,600 points wide and 240 to 1,200 tall; `atd.setState` at most 65,536 bytes; a message at most 10,000 characters. The widget frame takes its content's height between 32 and 240 px and cuts off the rest.
- Neither `html` nor `widget` may contain a document wrapper (`<!doctype>`, `<html>`, `<head>`, `<body>`), `<iframe>`, `<frame>`, `<object>`, `<embed>`, `<base>`, `<meta http-equiv>`, `<link>` or `<script src>`, nor `src`, `srcset`, `poster`, `data` or `background` attributes, or CSS `url()` or `@import`, whose value starts with `http:`, `https:` or `//`.
- Nothing loads from the network: no `fetch`, XHR or WebSocket, and no outside images, fonts, media, scripts or stylesheets. Draw images as inline SVG or `data:` URIs, and use the system fonts the kit sets. No `eval` or `new Function`, workers, pop-up windows, `alert`, `confirm` or `prompt`, downloads, cookies or web storage, and nothing navigates; don't rely on the clipboard or on file inputs. Get what the view needs yourself and pass it in `data`.
- `show_ui` and `update_ui` are yours alone: subagents don't have them, and a `codemode` script cannot call them.
- Never ask for passwords, keys, payment details or other secrets in a view: what the user enters becomes a message in the conversation. Never make a view look like the app's own prompts, approvals or settings, or like another app or a sign-in page. Never put untrusted content (web pages, files, mail, tool output) into `html`, `widget` or a script: pass it in `data` and show it as text.
