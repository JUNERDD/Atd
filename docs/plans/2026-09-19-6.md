# 聊天流式渲染 6 项优化

Status: Executed - implementation complete, live-visual confirmation remaining
Created: 2026-09-19
Approval: Approved by user 2026-09-20; executing all nine todos

## Summary

本次计划覆盖任务面板聊天流在流式过程中的 6 处体验修复，全部位于 `apps/desktop/src/features/agent/transcript/` 与 `apps/desktop/src/components/composer*`，复用 `packages/ui` 的 `ActivityRow`、`Shimmer`、`Popover`、`ScrollArea` primitives。

- 项目 1：流式中根工具展开链无法收起。根因是 `ActivityPhaseView` 的受控 `open=waiting||override===true` 在 `approvalPending` 时强制展开，且 `wasActive/active` 在 settled 时把手动 `override` 清空导致 snap-shut；`done/active` 由 `TurnView` 的 `settled/answering/activityStillRunning` 决定。
- 项目 2：根工具 icon 与文案未对齐。`ActivityRow.Trigger`（`Button ghost` + `activity-trigger`）与 `Icon/Title/Meta` 是共享行框架，但 redacted thinking 用了 divergent 的 `div.thinking-row>span(px-1.5 py-1 gap-2)`，`phase-single` 用 `gap6 + icon margin-top7`，与 `phase-group` 头部 padding/gap 不一致；另有 `phase-icon-swap/phase-body` 死选择器。
- 项目 3：thinking 流光与其他工具不一致。thinking live 只用纯 CSS `thinking-pulse`（整行 opacity 呼吸，1.8s），其余 live 文案（running tool、active phase、live turn、progressing history）统一用 `packages/ui` 的 `Shimmer`（motion 驱动 `backgroundPosition` 渐变扫过，2s linear，`--spread=len*2px`）。
- 项目 4：HITL 内联过重，需要收敛为工具名 + 输入框上方专用 popover。现状是 `ToolBlock` 行下直接挂 `ApprovalControls`（scope 标题 + Allow once/session/Decline），`QuestionBlock` 内联 chips + Skip；`Composer` 已收到全部 `requests` 但只用 `kind==='input'` 做输入占位与文本区回答，无上方 popover；最接近的既有模式是 `ModelConfigPopover/ModelPicker`（Radix Popover）与 in-flow 的 `ComposerQueue`。
- 项目 5：图三流式中 assistant answer 区空白，需要显示 token 速率。现状 `TurnHeader(live)` + `ActivityGroup(toolOneLive)` + 空 `assistant` 块（`isIgnoredBlock` 按设计丢弃空 answer）；`Block/IPC/renderer` 全链路无 usage/rate，Pi `AssistantMessage.usage` 在 worker 内存里存在但被 `projectAssistantBlocks` 丢弃，且 Pi streaming 的 usage 只在 final chunk 才有值。
- 项目 6：图四 `Jump to latest` 需要换成“滚动到底部”。现状 pill 只在“滚离底部后又有新 `revision`”时出现，handler 是 instant `scrollTop=scrollHeight`，idle 滚起时无按钮；容器是 Radix transcript viewport，`--overlay-footer-height` 决定 pill 位置。

计划策略：前 3 项与第 6 项做 renderer-only 收敛；第 4 项需要定义 popover 单例/队列、input/confirmation 覆盖范围、焦点与 Esc 冲突；第 5 项需要先定速率口径（renderer 字符估算可零 schema 改动，真 tok/s 需要 worker+schema+projection 全链路打通且 live 仍只能估算）。

用户已答复的新方向（2026-09-19）：项目 4 改为 HITL 与排队共用输入框上方同一个 popover、内部分区展示，现有排队 in-flow 渲染被认为有问题，需要评估最佳实践；项目 5 优先在 pi 生态找可用插件实现速率，而不是直接自研打通。后续调研将先补这两条证据再冻结契约。

补充结论（同日二轮调研）：统一 popover 推荐单容器双分区（上 HITL 紧急区、下排队区），`side=top` + Portal 针定 `composer-surface`，受控 open + 按视图管理焦点，Esc 需要拆分为关闭与拒绝两层语义；pi 生态无可用 live 速率插件（上游 usage 终值语义、TUI footer 仅累计、`json` 模式下 `setStatus/setFooter` 为 no-op、无第三方速率插件），最小自研边界为 live 用 renderer 字符估算（`chars/4`）、settled 用 worker 捕获真 usage 替换。

用户已接受统一 popover 推荐（单容器双分区 `side=top`）；速率已授权网络检索第三方 pi 插件，本地只读检索未发现可用实现，网络检索结论将回填到项目 5 引用与待办。

网络检索结论（同日）：找到 `pi-tps-status 1.0.5`（MIT，0 依赖，543/月）与 `pi-token-speed 0.10.1`（MIT，0 依赖，5805/月，peer `>=0.85.1` 恰好命中本仓 pin）。两者均通过 `@earendil-works/pi-tui` 状态条渲染，在本仓 worker 的 `json` 模式下 UI 通道为 no-op，无法直装生效；可复用算法为滑动窗口（默认 1000ms，最小跨度 250ms）、`estimate=ceil(chars/4)` 且 CJK 计 1、provider 终值回填平滑、工具执行暂停计时、TTFT、结束行为 average/last。复用决策：不直装插件，以 Electron 原生投影移植上述算法（live 估算 + settled 真值），并在实现中注明来源与差异。

后续细化（2026-09-20）：项目 6 的滚动按钮改为 `IconButton`（ArrowDown，复用 `conversation.scrollToBottom` 文案做 tooltip），表面为 `styles.css` 的 `.scroll-to-bottom` 浮层（`--popover` 75% 微透明 + `--ata-backdrop-blur` 模糊 + 边框阴影），定位与显示逻辑不变；点击改为平滑滚动（`prefers-reduced-motion` 下保持 instant，live 跟随与 resize 仍 instant）。
